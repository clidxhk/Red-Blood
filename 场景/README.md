# 场景策划层

`场景/` 保存“某一次具体场面如何准备”的策划卡，不保存人物底谱、世界地点正文、正式时间线或审定故事。它是创作管线的中间层：向上承接世界与人物事实，向下生成导演、写手和人物发言者的输入包。

## 五层分工

| 层 | 主要入口 | 负责回答 | 不负责 |
| --- | --- | --- | --- |
| 人物层 | `角色/` | 这个人是谁，稳定性格、关系、能力与经历如何 | 这一场临时知道什么、想做什么 |
| 世界层 | `世界/` | 哪些法理、地点、势力、器物长期成立 | 某场戏怎样开局和收束 |
| 场景层 | `场景/` | 这一次何时、何地、何人因何入场，冲突怎样推进 | 替代正式设定、故事正文或连续性记录 |
| 连续性层 | `故事/` 中的时间线、审定正文与系列说明 | 已经发生了什么，下一章必须接住什么 | 尚未采纳的试演方案 |
| 组装层 | `scripts/scene_runtime/` 与 `.workbench/runs/` | 如何核验来源、裁剪权限并生成三类输入包 | 自动判断文学质量、人物动机或事实真伪 |

`故事/茶馆闲聊/场景/` 中现有的 [[偏街旧茶馆]]、[[回青医馆]]、[[保和丹铺]]属于**场所正文**，说明这些地方长期是什么样。根目录 `场景/` 则记录**具体场次任务**，说明这一次在这些地方发生什么。两类文件不互相替代。

## 场景卡应装什么

普通场景先在任务依据表中简记本场必要性与承接、人物目标、关键选择及代价、结尾变化、视点与披露、必要来源和回填项。无需另建卡、目录或清单；静场与过渡可只改变读者理解或情绪。长期复用时可保存一张卡；以下内容和完整模板均为按需扩展，不要求逐格填满：

- 目标篇章、时间轴节点、回目或章节的承接位置。
- 地点入口、时令天候、空间限制、声音气味与灵机等感官锚点。
- 人物槽位：为何在场、本场目标、开场状态、知道什么、能说什么、何时离场。
- 戏剧问题、开场触发、冲突线、节拍、必须透露、可暗示与禁止透露。
- 场外压力、物件位置、伤势、费用、巡禁、传讯等会影响判断的临时条件。
- 退场后的连续性变化，以及需要回填时间线、人物 MD/JSON 或世界正文的触发项。
- 已核验的来源路径与适用范围；需要精确组包时，再把这些来源写入 `scene_runtime` 清单。

人物槽位只提炼本时点成立的材料。完整人物卡留在 `角色/`；场景卡不复制稳定设定，也不以临时目标覆盖长期动机。

## 场景卡不应装什么

- 整篇人物正文或完整 JSON 底谱。
- 整章地点志、势力总纲或历史叙述。
- 已审定正文的改写稿；草稿和生成包放在 `.workbench/`。
- 尚未采纳的试演对白被直接写成世界事实。
- 自动摘要、模型推测或无出处的“应该有”。
- 一张卡包办多章、多个平行时点或多个互相排斥的分支。

## 文件与状态

需要长期复用时按系列和场次保存 `策划.md`；只有复杂信息隔离、多分支或可重放需求才增加 `scene.json`。以下目录展示启用了运行清单的归档形式：

```text
场景/
├── README.md
├── AGENTS.md
├── 模板/
│   ├── 单场景策划模板.md
│   └── 茶馆夜话策划模板.md
└── 茶馆闲聊/
    └── 第一回开场/
        ├── 策划.md
        └── scene.json
```

其他系列使用相同目录形式，例如 `场景/炎帝崛起/<卷章与场面短题>/`，有实际任务时再创建。
`策划.md` 记录本场创作判断，选填空间、节拍等扩展内容；启用运行工具后，`scene.json` 才记录完整的核验来源、时点、人物状态和逐人披露。v1 不支持的创作字段仍留在策划中，工具不自动转换策划。来源路径从仓库根目录起算，候选分支和生成包留在 `.workbench/runs/`。

场景卡状态统一使用以下五种：

| 状态 | 含义 |
| --- | --- |
| `策划中` | 仍在查证、选材与补缺口 |
| `待预演` | 仅在已决定启用预演时使用，具体难题与人物边界已明确 |
| `待成文` | 本场变化、视点和来源已明确；未预演可直接到此，有分支时已选定 |
| `已审校` | 正式正文和适用审校均已通过 |
| `已回填` | 时间线及必要的人物或世界条目已同步更新 |

状态只说明流程位置。`已审校`之前的内容都不是正式事实，生成包和试演分支也不因保留在文件里而自动获得采纳资格。

## 使用顺序

1. `research-agent` 检索必要依据，核查时间线、地点、人物在位与认知边界；茶馆任务另经 `teahouse-chronicler` 专项增补。
2. 在依据表中明确本场变化与视点。长期复用时可用[单场景模板](模板/单场景策划模板.md)或[茶馆夜话模板](模板/茶馆夜话策划模板.md)存为 `策划.md`；扩展栏按需选用。
3. 主架构师简记具体难题与是否启用独立预演；不因人数自动触发。决定启用后调用 `character-actor`，试必要片段或对照方案，问题解决或无新价值即停。复杂信息隔离、多分支或可重放任务再启用运行清单，启用后完整校验来源与授权。
4. `style-writer` 直接统稿；预演如有，仅作可自由剪裁的材料。作者/写手真相、人物知道/相信/能说什么、读者在本段视点获知什么分别判断，写手可获伏笔所需真相，人物未知秘密不得交演员。
5. 正文走语气、交叉引用、人物与必要的跨文件一致性审校。文学验收看本场必要性、选择与代价、关系/认知/处境或读者理解的变化，以及继续阅读动力；静场不强求争斗反转，程序通过不能证明质量提升。
6. 正文正式采纳后回填连续性和长期变化；人物 MD/JSON 按时序更新，保留先前阶段。若保存了场景卡，再标记相应状态。

## 后续同场景对照试用

后续选同一场景，以相同依据、目标和视点分别尝试“写手直接统稿”与“围绕具体难题按需预演后统稿”，使用相同适用审校比较人物声音、情节推进、所需修改量和总耗时；记录实际预演范围及停止原因。结果可支持任一方案或因场景而异，不预设胜者。本次只设计方法，未执行新试用；既有回放记录及数字保留，技术校验不计作人物预演或新正文验证。

场景卡受双链目标检查保护，但本身不进入正式双链目标集合。可对单张卡执行 `python scripts/check_crossrefs.py --check-links "场景/具体卡.md"`，检查其引用是否指向真实且唯一的正式文件。
