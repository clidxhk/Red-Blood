# 赤血（Red Blood）

**License:** Creative content under [CC BY-NC-SA 4.0](./LICENSE); code and tooling under [MIT](./LICENSE). See the [LICENSE](./LICENSE) file for scope and details.

> 一个把仙侠世界观做成可协作知识网络的尝试。  
> 用 Obsidian 串联设定，用 Git 保留演化脉络，用协作智能体辅助检索、补缀、扩写与回填。  
> 一起把一座能生长、能回链、能接力的仙侠世界慢慢写出来。

---

## 项目是什么

`赤血（Red Blood）` 不是单一小说稿，也不是零散灵感堆栈，而是一座持续生长中的修仙 / 玄幻世界观仓库。

这里既有天地底层规则、九州与神族两套文明机器的长期对冲，也有州域、门阀、人物、器物、异类、茶馆闲谈与地方生计。宏大叙事和贴地日常被同时织进同一张互相引用的网里。

这个项目想解决的，不是"有没有点子"，而是：

- 让多人可以围绕同一个世界持续接力，而不是各写各的平行草稿。
- 让设定具备可检索、可修订、可回链、可追溯的骨架。
- 让 AI 协作建立在既有世界观之上，而不是脱离上下文即兴编造。

## 为什么适合协作

### Obsidian

Obsidian 在这里不只是笔记软件，更是世界观操作台。

- `[[双链]]` 用来把人物、势力、州郡、器物、历史事件彼此咬合在一起。
- 图谱视图能直观看到哪些概念已经长成网络，哪些条目仍然孤悬。
- 回链、搜索和大纲视图，适合做设定回填、命名统一和结构整理。

如果需要改文件名，务必在 Obsidian 里操作，让它自动更新双链引用，避免整批链接失效。

### Git

Git 在这里承担的是集体记忆骨架。

- 每次补设定、重写条目、回填旧文，都留下清晰的版本脉络。
- 不同作者可以并行推进不同州域、人物或故事线，通过提交历史回看演化过程。
- 对世界观工程来说，版本控制不只是备份，更是防止设定漂移的工具。

### 协作智能体

这个项目把 AI 放在检索、对齐、补缀、扩写的位置，而不是让它脱离设定直接代写。协作不再依赖单个智能体"读完所有设定再写"，而是由一个总导演调度八个专项 subagent，按四阶段管线协作推进。

- [`AGENTS.md`](./AGENTS.md) 定义了一个八人 subagent 团队：`research-agent`（检索调研）、`teahouse-chronicler`（茶馆专属约束）、`character-actor`（人物互动预演）、`style-writer`（正文撰写引擎）、`tone-checker`（文风语气审校）、`crosslink-checker`（交叉引用审校）、`character-reviewer`（人物七维审查）、`worldbuilding-consistency`（跨文件八维一致性审查）。
- [`MEMORY.md`](./MEMORY.md) 索引了长期有效的协作记忆，帮助后续轮次更快接住上下文。

这样做不是为了省掉创作判断，而是让多人协作和多轮 AI 协作走同一套轨道——每一条创作任务都经过检索→撰写→审校→交付四个强制阶段，每个阶段有明确的负责 subagent 和产出物。

### 多 Subagent 协同机制

`AGENTS.md` 的核心设计是"总导演 + 专项 team"。主架构师负责判断任务类型、调度 subagent、审核产出、处理审校意见后交付；八个 subagent 各自专精一个管线阶段，不跨越阶段、不越权撰写。

- **管线不可跳过**：阶段一（`research-agent` 检索调研）未完成，不得进入阶段二（`style-writer` 正文撰写）；阶段三（多维审校）未全部通过，不得进入阶段四（交付）。
- **按任务类型路由**：新建条目走 `research-agent → character-actor → style-writer → tone-checker → crosslink-checker → character-reviewer` 六环链路；茶馆回目额外插入 `teahouse-chronicler`；批量统稿追加 `worldbuilding-consistency`。
- **审校不修改正文**：阶段三的四个审校 subagent 只出报告，修正由主架构师亲自执行，确保修改可追溯、不引入新噪音。
- **并行与依赖**：`tone-checker` 和 `crosslink-checker` 可并行调用，`character-reviewer` 和 `worldbuilding-consistency` 可并行调用，但两组间有依赖顺序——前一组可能产生需要后一组重新检查的修正。

### 场景策划与运行层

在四阶段管线内，先用场景卡确定“这一次在哪里、谁因何在场、争什么、能透露什么”，再把核验过的材料组成设定包，分别提供给导演、写手与人物发言者。开场事实、个人信念、言谈分寸与候选事件分别记录，分支试演不自动改写正式设定。

- [场景策划统一入口](./场景/README.md)：五层分工、场景卡内容、状态与使用顺序。
- [场景层规范](./场景/AGENTS.md)：策划边界、来源要求与回填纪律。
- [修改路径与分阶段验收](./scripts/scene_runtime/PLAN.md)：职责修复 → 数据协议与离线工具 → 已完回目回放 → 后续真实创作试用。
- [协议与使用说明](./scripts/scene_runtime/README.md)：来源哈希、时间范围、逐人可见性、字符预算及分支规则。
- [第一回开场回放材料](./scripts/scene_runtime/examples/teahouse-replay.json)：从原文摘取的环境和两名人物语态，不续写对白或新增事件。

工具入口为 `python scripts/scene_runtime.py`，支持 `validate`、`build`、`fork`；实际生成包保存在忽略于 Git 和内容索引的 `.workbench/runs/`。工具仅验证和组装文件，不调用模型或隔离文件权限，真实预演与审校仍由主架构师调度。`场景/` 策划卡不进入正式双链目标集合，也不会被接受为正式正文来源；可单独检查卡内引用是否有效。

指定内容范围的双链目标检查使用 `python scripts/check_crossrefs.py --check-links <文件或目录>`，可发现死链、错名与同名歧义；原裸词模式继续辅助发现漏链。完整验证运行 `python -m unittest discover -s scripts -p "test_*.py" -v`。

## 当前内容覆盖

- **经济体系**：货币、能源、购买力对照与多品类价格表已形成基准框架
- **器物与功法**：九州法器与神族器物双线推进；功法囊括赤血专属内功、星辉三诀、九州五行法术，以及参考经典著作意象转译的神族宏域法术律令群（《白原诵》《诸神纪谱》《原富隐手》《四音叩命》《先命简黜》《百曲引魂》《谪星》等）

## 如何参与

### 打开方式

- 优先用 Obsidian 打开整个仓库
- 从根目录进入，保留双链、回链和图谱能力
- 重命名文件时不要在文件管理器里直接改名

### 协作前先读

如果要补设定、扩写条目或回填旧文，建议先过一遍：

- [`AGENTS.md`](./AGENTS.md)
- [`世界/背景/世界背景.md`](./世界/背景/世界背景.md)

- 先检索，再下笔，不脱离现有设定即兴编造

- 涉及人物时，正文与对应 `json` 底谱同步维护
- 尽量延续既有命名、语气、时代感与世界内部叙述方式

## AGENTS.md 如何接入不同工具

主规则文件只有一份：根目录的 [`AGENTS.md`](./AGENTS.md)。

### Antigravity

Antigravity 会自动加载工作区根目录的 `AGENTS.md` 作为核心系统规则，原生支持智能体管线调度与工具交互。

### Codex

Codex 在仓库根目录启动时会直接读取 `AGENTS.md`。

### Claude Code

根目录 [`CLAUDE.md`](./CLAUDE.md) 当前内容为：

```md
@import AGENTS.md
```

Claude Code 通过导入方式复用主规则。

### Gemini CLI

[`.gemini/settings.json`](./.gemini/settings.json) 当前配置为：

```json
{
  "context": {
    "fileName": ["AGENTS.md"]
  }
}
```

Gemini CLI 会把 `AGENTS.md` 注入会话上下文。

最稳妥的约定：

- 规则只维护一份主文件：`AGENTS.md`
- Antigravity 自动加载工作区主规则
- Claude Code 通过 `@import` 接入
- Gemini CLI 通过 `context.fileName` 接入
- Codex 在根目录直接读取
