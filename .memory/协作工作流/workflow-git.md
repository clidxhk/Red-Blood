name: workflow-git
description: 每轮完工即时精确提交并汇报哈希；并行环境严禁批量暂存，严格防范中文路径假阴性
type: feedback
---

规则一：每轮文件修改（新建、扩写、重构、旧文回填）完工后，必须立即执行 `git add <实际改动文件>` 与 `git commit`，将修改真实写入 Git 提交历史，并向用户如实汇报提交哈希与变更文件数；严谨使用术语，不把“已暂存”（staged）与“已提交落库”（committed）相混淆。

规则二：提交改动时，仅可逐一显式指定 `git add -- <本次任务实际修改之文件>`，严禁滥用 `git add -A`、`git add .` 或 `git commit -a`。若开工前工作区干净，收尾时却发现大量未曾触及之陌生变更，表明有并行会话在同一工作区协同作业——此时严禁顺带提交他人文件，仅提交本任务改动之文件，并将他人修改留存于工作区且在汇报中明确说明。

规则三：若同一文件出现本会话与并行会话的混合修改（例如《起源总纲.md》既包含本任务的回填，又包含他人新增论述），严禁粗暴整文件提交。应先借助 `git diff` 厘清改动权属；若双方改动交织难以剥离，宁可暂缓提交该文件并向用户请示，亦不可将他人半成品强行提交落库。若混合改动在行级能够清晰分离，可通过对照 `git show HEAD:<path>` 确认行号后构造细粒度 patch，运用 `git apply --cached <patch>` 仅将本任务改动暂存进 index，使工作区双方改动和谐共存。

规则四：Windows + Git Bash 环境下，若使用 `git diff --quiet -- "中文路径.md"` 检测文件状态易产生假阴性（中文参数经 shell 编码转换后与 Git 内部编码不一致，导致已改动文件被误判为未变动）。检测文件干净与否改用 `git status --porcelain -z`，或在 Python 中通过 `subprocess.run([...])` 以列表原生传参，杜绝依赖 shell 内联拼接的中文路径字符串。

**原因：** 用户多次发现此前仅执行了暂存而未真正提交落库，造成信息误解与重复核验；本仓库常有多会话并行作业，批量暂存曾险些将并行任务的半成品误行提交；而中文路径在特定 shell 下的假阴性问题亦曾险些误判文件状态。

**应用场景：** 本仓库所有创作与维护任务的收尾落库环节：先以 `git status --short` 与 `git diff --stat` 校验变更范围，逐个文件显式 add，commit 后向用户汇报提交哈希；遇非预期改动时先 diff 辨明归属再行定夺。
